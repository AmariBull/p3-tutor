Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in a saved note, or in a manual that the assistant searches when it needs it.

Objective O3: context and memory in an agent About 30 minutes Builds on the agent loop (your learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals, and it must remember each student's training status between visits. Both are memory problems, and both cost money. At your design review, "what does it keep, and where?" will be one of the first questions.

Warm-up 2 min

Recall

From the agent loop: after the program runs a tool the model asked for, what does it do with the result? Answer in one sentence before you open the box.

Check your answer

It puts the result into the model's next input and calls the model again, so the model can choose its next step or write the final answer. Today's whole topic hides in the words "next input": that input has to hold everything the model needs to know, and it is finite.

Recall

A model writes text one token at a time. Without looking back, what do you think a token is?

Check your answer

A token is a small chunk of text, often a short word or part of a longer word. Models read and write in tokens, and usage is counted and billed in tokens. You will see why that matters for your budget in a few minutes.

The context window: everything the model sees 6 min

Start with a concrete case. A student types: "How do I change the blade on the bandsaw?" Before the model writes a word, the program assembles a bundle of text and sends it. The bundle holds the assistant's instructions ("You help students at the university makerspace..."), the descriptions of its tools, and the student's question. The model reads that bundle and replies.

The context window is the model's entire working input for one call, measured in tokens, and it has a maximum size. The context is whatever you actually put in it. The model sees nothing else: not your code, not the booking database, not yesterday's chat. If a fact is not in the context for this call, the model does not have it. Anthropic's documentation describes the window as the model's "working memory" and notes that it is separate from the data the model was trained on (Claude Platform Docs: context windows).

Two consequences for your budget. First, the window is a hard limit: once the context would exceed it, something must be dropped or the call fails. Second, you pay by the token for what you send, not only for what the model writes. A bigger context is a bigger bill on every call.

Window sizes differ by model and change often, so look up the number for the model your team picks rather than memorizing one. The docs page above lists them.
A common mix-up

"The model remembers what we talked about, like a person does." It is tempting because chat apps feel continuous. But the model itself keeps nothing from one call to the next. The program re-sends the earlier conversation each time, and that is the only reason the model appears to remember. Take away the re-sent text and the model starts blank.

Check yourself

Your booking system has 3,000 entries for next month. A student asks whether the 3D printer is free Thursday. Which statement is true of the model's call?

Show the answer

The third option. The model sees only its context, so the calendar tool has to fetch the Thursday entries and the program has to put them into the next call. Sending all 3,000 entries would waste tokens; fetching one machine and one day is cheaper.

Between steps: the transcript grows 6 min

Now put the window inside the agent loop. Every step is a separate model call, and the model keeps nothing between calls. So to let the model see what happened so far, the program keeps a running list of messages, the transcript: the question, each tool request, each tool result. On every call, it sends the whole transcript again (Anthropic Engineering: effective context engineering).

That is what "kept between steps" means: the program keeps the transcript, in an ordinary Python list, and re-sends it. Here is a worked count with made-up but plausible numbers. The instructions and tool descriptions take 2,000 tokens, the question 100, and each tool result adds 1,500. We ignore the model's short replies.

Model callWhat is sentInput tokens
1fixed 2,000 + question 1002,100
2call 1 + one tool result3,600
3call 2 + one tool result5,100
4 (final answer)call 3 + one tool result6,600
Total billed17,400

The final context is only 6,600 tokens, yet you paid for 17,400 input tokens, because early text is re-sent on every call. Cost grows faster than the number of steps, and long runs get expensive quickly. (Some providers discount re-sent text through caching; check your provider's pricing, but do not assume it.)

There is a second cost, and it is about quality rather than money. Anthropic's engineers describe a finite "attention budget": as the number of tokens grows, the model's ability to recall information accurately from the context tends to decrease, an effect they call context rot. Their advice is to find the smallest set of high-signal tokens that gets the job done (Anthropic: effective context engineering for AI agents). More text is not automatically better.

A common mix-up

"A bigger context window means I can stop worrying about context." Quiz 0001 had a related trap. A larger window raises the ceiling, but you still pay for every token on every call, and a crowded context can make the model worse at using what is in it. The window is a limit, not a goal to fill.

Keeping the window tight 4 min

If the transcript only grows, long runs eventually hit the limit and cost too much on the way. So the program edits it. Three common moves, all described in Anthropic's guidance for long-running agents (engineering post, context management announcement):

  • Clearing old tool results. Once the model has used a big manual page, delete that page from the transcript and keep a one-line note that it was read. This is usually the cheapest, safest edit.
  • Compaction. When the context nears the limit, ask the model to write a short summary of the conversation, then start a fresh context holding that summary. You trade detail for room.
  • Returning less in the first place. A tool that returns one section of a manual instead of the whole manual needs no clearing later.

Every one of these loses information, so choose what to drop deliberately. A discarded detail the model needs later cannot be recovered from the context; it has to be fetched again or it is gone.

Which tool results can be cleared is a design decision. A bandsaw manual page can be cleared after the answer is written. The student's training status, which later steps depend on, should not.

Between sessions: the model remembers nothing 5 min

When the student closes the chat, the transcript is gone unless your program saved it. A new session starts with an empty context. So if a student was certified on the laser cutter last Tuesday, the assistant will not know it tomorrow unless something puts that fact back into the new context.

That something is external memory: information stored outside the model, in ordinary storage your program controls, and loaded into the context when it is useful. Two forms matter for you.

Records in a database

The training status of each student is structured data: student id, machine, date certified. Keep it in a table or JSON file. At the start of a session, the program (or a tool such as check_training_record) reads that student's rows and adds a line to the context. This is exact, cheap and easy to audit, and it needs no clever AI at all.

Notes the agent writes for itself

For open-ended work, an agent can write notes to a file as it goes and read them back later, so progress survives a cleared context or a new session. Anthropic calls this structured note-taking, memory kept outside the context window and pulled back in when needed (engineering post). Anthropic's memory tool is one version: the model asks, through tool calls, to create, view or edit files in a memory directory, and your application carries out those requests against storage you control (memory tool docs). It follows the same loop you already know: the model requests, the program acts. Anthropic reports that using the memory tool together with context editing improved performance on a long-running agentic task set over a baseline (announcement).

A common mix-up

"Memory means the model learns from our chats." No. Saving a note changes your storage, not the model; its trained knowledge stays as it was. Memory only works because the saved text is put back into a later context. If the load step is missing, the note might as well not exist.

Retrieval: finding the right page 5 min

Your manuals are long. The assistant cannot put them all into every call, and it should not: you would pay for them every time, and context rot works against you. Instead it fetches only the relevant part when a question arrives. This is retrieval: searching a store of documents for the few pieces that bear on the current question, and adding just those to the context.

A concrete case. A student asks, "What speed should I run the bandsaw for aluminum?" The program has already prepared the manuals by splitting them into chunks, pieces of a few paragraphs, and indexing them. At question time it searches the index for the best-matching chunks, takes the top few, and puts them in the context with the question. The model answers from them, and ideally says which manual they came from.

Two ways to search are common. Keyword search (for example BM25) matches the exact words, which is good for part numbers and error codes. Embedding search matches meaning, so "cutting speed for metal" can find a chunk that says "feed rate for non-ferrous stock". Anthropic's contextual retrieval write-up reports that combining both beat either alone, and that a chunk cut out of a manual often loses what it refers to, so adding a short note about where the chunk came from improved results (Anthropic: contextual retrieval).

Retrieval can be a step the program always does, or a tool the model chooses to call. Letting the model search "just in time" with a tool such as search_manuals(machine, query) keeps context small and lets the model look again with a better query; Anthropic describes coding agents that work this way, pulling in files only when needed (engineering post).

The same post says that if your whole knowledge base is under roughly 200,000 tokens, you may be able to put it all in the prompt and skip retrieval. Check the manuals' total size, and your per-call cost, before building a search system.
A common mix-up

"Retrieval means the model looks things up in the manuals itself." The search runs in your program or in a tool the program executes. The model only sees whatever text comes back. If the search returns the wrong chunk, the model will answer from the wrong chunk, confidently, so test retrieval separately from the model.

Worked example and practice 6 min

Worked example

A student who was certified on the laser cutter two weeks ago opens a new chat: "Can I book the laser cutter Friday, and what material settings do I use for 3 mm acrylic?" Decide where each piece of information lives and how it gets into the context.

  1. List the facts needed: the student's certification, Friday's availability, the acrylic settings, and the assistant's rules.
  2. Rules and tool descriptions: the same for every student and every call, so they sit in the context every time. Keep them short, because you pay for them on every call.
  3. Certification: this is from a previous session, so it must be saved. A check_training_record tool reads it from the database and returns one line. The model learns the fact only when that line arrives.
  4. Friday's availability: changes constantly, so it is never stored in memory. check_calendar fetches only that machine and day.
  5. Acrylic settings: in the manuals, so search_manuals retrieves a few chunks. Once the answer is written, those chunks can be cleared from the transcript.
  6. Cost check: three small results instead of whole manuals and a full calendar, so each call stays small.
Your turn

The assistant's fixed text is 2,000 tokens and the question is 100. Call 1 sends those 2,100. The tool then returns a manual page of 8,000 tokens, so call 2 sends 10,100. A second tool returns 500 tokens, and call 3 writes the answer. First, compute the total input tokens billed over the three calls. Second, say by how much clearing the 8,000-token page before call 3 would cut the total, and what you would keep in its place.

Show a solution

Without clearing: call 1 is 2,100, call 2 is 10,100, and call 3 is 10,100 + 500 = 10,600. Total 22,800 tokens. With the page cleared before call 3, call 3 sends 2,100 + 500 = 2,600, so the total is 2,100 + 10,100 + 2,600 = 14,800, a cut of 8,000 tokens. In place of the page, keep a one-line note such as "Read acrylic settings from the laser cutter manual", plus any specific values the model needs for the final answer, since those cannot be recovered once removed. Note the tension: if the settings themselves are the answer, call 3 needs them, so clear a page only after its useful content has been used or noted.

Summary 2 min

  • The context window is everything the model sees on one call, with a token limit; you pay for it on every call.
  • Between steps, your program keeps the transcript and re-sends it, so cost grows faster than the step count. Trim by clearing old tool results, compacting, and returning less.
  • Between sessions the model keeps nothing. Save records and notes in storage you control, and load them into the context when needed.
  • For long manuals, retrieve a few relevant chunks per question instead of loading everything; keyword plus meaning-based search works best.
