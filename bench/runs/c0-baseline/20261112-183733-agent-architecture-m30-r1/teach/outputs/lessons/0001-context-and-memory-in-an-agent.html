Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it lives in the context window, in saved notes, or in a searchable manual store, and say why.

Objective O3: context window, what is kept between steps and sessions, retrieval and notes as memory About 30 minutes Builds on the agent loop (quiz 0001)
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits, all on a small model budget. Those three needs (long manuals, memory across visits, low cost) are exactly what this lesson is about, and they are choices you will defend at your design review.

Warm-up 2 min

You already know the agent loop: the model asks for an action, the program runs it, the result goes back, and this repeats. Try one recall question before we build on it.

Recall

A student asks, "Is the laser cutter free tomorrow, and do I need training?" The assistant calls check_calendar, then check_training_record, then answers. How many times was the model called, and what does the model do between calls?

Check your answer

Three model calls: one that asks for the calendar, one that asks for the training record, and one that writes the final answer. The model does nothing between calls: it is not running. The program runs the tool, then makes a fresh call. Today's question is what that fresh call contains.

What the model sees: the context window 6 min

Start with a concrete case. A student types: "How thick can I cut on the bandsaw?" Your program builds a request for the model. It does not send only the question. It sends a bundle:

  • the system prompt: your standing instructions ("You are the makerspace assistant. Be brief. Never book without confirming.");
  • the tool definitions: the names and descriptions of check_calendar, search_manuals and the rest;
  • the conversation so far: earlier student messages, earlier model replies, and earlier tool results;
  • the new student message.

The context window is all the text the model can look at when it writes a response, including the response itself. Anthropic's documentation calls it the model's "working memory", and says it is different from the large body of text the model was trained on (Claude docs: Context windows). Everything in the request counts: the system prompt, every message including tool results, and the tool definitions. The model's own output counts too.

Text is measured in tokens, the small chunks of text the model reads and writes. Roughly, a short common word is one token and a long or unusual word is several. Tokens are the unit for both the window's size limit and your bill, which is why the window matters for your sponsor's budget.

A common mix-up

"The model remembers our conversation, like a person does." It is tempting because chat apps feel continuous. But the model keeps nothing between calls. What feels like memory is your program sending the earlier messages again each time. If the program leaves something out of the request, then for the model it never happened.

Check yourself

Your assistant has a 1,200-token system prompt, and its tool definitions take 800 tokens. A student sends a 40-token question. Roughly how much of the window is used before the model writes anything?

Show the answer

About 2,040 tokens: 1,200 + 800 + 40. The system prompt, tool definitions and question all sit in the window before the first word of the reply.

Between steps: the context grows 6 min

Now the loop. Inside one session, what is kept between steps? Everything. Anthropic's documentation describes this as progressive accumulation: each message and response is added to the window, and previous turns are preserved completely (Claude docs: Context windows). A tool result is no exception: when search_manuals returns four pages, those pages are appended to the conversation and sent on every later call.

That gives two consequences you will meet in your design.

Consequence 1: cost grows faster than the number of steps

Each call re-sends the whole history as input, so a step late in the loop is more expensive than an early one even when it asks for something small. A result that is 3,000 tokens long is not paid for once; it is paid for in every call after it arrives. (Prompt caching can lower the price of re-sent tokens, but the docs are clear that cached tokens still occupy the window: it changes what you pay, not whether they count.)

Consequence 2: more is not better

Anthropic's engineers describe context rot: as the number of tokens in the window grows, the model's ability to accurately recall information from it decreases. They treat context as a finite resource with an "attention budget", and the goal as the smallest set of high-signal tokens that gets the job done (Effective context engineering for AI agents). So a big window is a limit on what is possible, not a reason to fill it.

Window sizes vary by model, and some current models accept up to a million tokens. Check the current figure for the model you pick; the design rule stays the same either way.
Check yourself

A loop runs eight steps. At step 8 the assistant asks for something tiny, a single date. Why is that call still the most expensive one in the run?

The third option. Each call's input is the whole history so far, so the last call has the longest input even if its own question is tiny.

When it gets too big 4 min

If a session runs long, the program can shrink the context instead of letting it grow. Anthropic's post names these levers (Effective context engineering; the docs also describe them as compaction and context editing):

  • Tool result clearing: delete old tool results that are no longer needed. The calendar answer from ten steps ago can go once the booking is made. This is one of the lightest forms of trimming.
  • Compaction: when the context nears its limit, have the model summarise it and start a fresh window from the summary. The hard part is deciding what to keep, because detail dropped from the summary is gone.
  • Sub-agents: give a focused job to a separate model call with a clean window, which returns only a short summary of its work. Whether that pays off is a later lesson.

For a makerspace assistant, most sessions are short: a question, one or two tool calls, an answer. You will likely rarely need compaction. What you will need is to keep each tool result small, which is what the retrieval section is about.

Between sessions: notes as memory 6 min

Everything so far lives inside one session. When the session ends, the context is gone. On Wednesday a student starts a new chat, and the model has no idea that on Monday they finished laser cutter training. Nothing carries over unless your program saved it somewhere and put it back into the next request.

This is memory in an agent: information saved outside the context window, in a file or a database, that the program or the model can load into a later context. Anthropic's engineers call the agent version structured note-taking: the agent writes notes to storage outside the window and reads them back later. Their example is an agent playing a game that keeps tallies and objectives across thousands of steps, and picks up from its own notes after its context is reset (Effective context engineering). A to-do list or a NOTES.md file is the simplest form. (This very workspace works that way: your tutor reads NOTES.md at the start of every session.)

Worked example: the training record

Monday, session 1: the student passes the laser safety check.

  1. The model calls a tool such as save_training(student_id, "laser", "passed"). The program writes a row in the makerspace's database. This is the memory.
  2. The session ends. The context window is discarded. The row stays.
  3. Wednesday, session 2: the program starts the new context with the system prompt, the tools and a new question. The record is not there yet.
  4. The model calls check_training_record(student_id). The row comes back as a tool result and now sits in this session's context, where the model can use it.

Memory outlives the session; context is rebuilt each time. Memory only helps once it has been loaded into the context.

Anthropic offers a ready-made version, the memory tool: Claude can create, read, update and delete files in a /memories directory that persist between sessions. It is client-side: Claude only requests the file operations, and your own application runs them against storage you control (Claude docs: Memory tool). That is the same loop you know: the model asks, the program acts, the result returns. The idea works with any model; you could build it with two tools, read_notes and write_notes.

A common mix-up

"A bigger context window gives the assistant memory." It is tempting because both sound like "how much it can remember". But a window only holds the current session. A million-token window still starts empty on Wednesday. Memory across sessions needs storage outside the window, and a program that loads it back.

One design question follows: what is worth saving? Save facts that stay true and will matter later (training status, a student's preferred machine). Do not save what is stale by tomorrow (whether the laser was free at 3 pm). A stored calendar answer is a wrong answer waiting to happen. Fetch live things live, with a tool.

Long manuals: retrieval 6 min

Your third need: answering from long machine manuals. The first idea is to paste a whole manual into the context. Sections 2 and 3 show why that fails for a small budget: you pay for every page on every call, and more text can mean worse recall. The second idea is retrieval: keep the manuals outside the context, in a searchable store, and bring in only the few passages that match the question.

A common setup works like this. Before any question, you split each manual into chunks of a few paragraphs and index them. At question time a search_manuals tool finds the best-matching chunks and returns them as the tool result. The model reads those and answers. It is the same agent loop, with the search as the tool.

Two ways to match a question to chunks:

MethodHow it matchesGood atWeak at
Keyword search (BM25)Counts shared words and exact stringsExact terms, such as an error code "E-47" or a part numberA question worded differently from the manual
Embedding searchCompares the meaning of the question and each chunk"How do I cut thick plastic?" finding a page about "acrylic sheet limits"Exact strings and rare codes

Anthropic's retrieval write-up uses this exact weakness as its example: a query for the error code "TS-999" may be missed by an embedding model, while BM25 finds the literal string. They combine both methods, and report that adding context to each chunk before indexing, plus a reranking step, cut the share of failed retrievals considerably in their tests (Contextual Retrieval). Those are their figures on their data; treat them as a direction, not a promise for your manuals.

There is a design choice about timing, too. Anthropic's post describes just-in-time retrieval: the agent keeps light references (a file path, a stored query) and loads content with tools when it needs it, instead of loading everything up front. It also describes a hybrid: load a little up front for speed (your short safety rules, perhaps in the system prompt) and let the agent fetch the rest. Runtime fetching is slower, so it needs good tools (Effective context engineering).

A common mix-up

"Retrieval means the model looks things up on its own." The model does not search anything itself. It writes a tool request with a query, your program runs the search, and the chunks come back as text in the context. How good the answer is depends on how good the chunks are, so a bad split or a bad query gives a confident answer from the wrong page.

Check yourself

A student asks, "What feed speed should I use for 6 mm acrylic on the laser?" The manual's page says "cast acrylic sheet, 5-8 mm, 15 mm/s". Which retrieval method is most likely to find that page, and why?

Show the answer

Embedding search is the best single choice for a loosely worded question. A hybrid of keyword and embedding search covers both loosely worded questions and exact codes.

Worked example and practice 8 min

Now put numbers on a context. These token counts are made up to keep the arithmetic easy.

Worked example: the cost of one request

The assistant has a system prompt and tool definitions that total 1,500 tokens. The student's question is 50 tokens. The model makes three tool requests of 50 tokens each, then writes the answer. The tool results are 300 tokens (calendar), 3,000 tokens (manual search) and 150 tokens (training record). How many input tokens are processed across all four model calls?

  1. Call 1. Input = 1,500 + 50 = 1,550. The model replies with the calendar request.
  2. Call 2. Input = call 1's input + the 50-token request + the 300-token result = 1,550 + 350 = 1,900. Everything earlier is re-sent.
  3. Call 3. Input = 1,900 + 50 + 3,000 = 4,950. The big manual result enters here.
  4. Call 4. Input = 4,950 + 50 + 150 = 5,150. The 3,000 tokens of manual are re-sent a second time.
  5. Total. 1,550 + 1,900 + 4,950 + 5,150 = 13,550 input tokens, even though the final context holds only 5,150 tokens.

The lesson in the numbers: the manual result is 3,000 tokens in the window but 6,000 tokens of processing, because it rides along on two calls.

Your turn

Same run, but a careless search_manuals returns the whole 40,000-token manual instead of 3,000 tokens of chunks. Step 1 is done for you: call 1 and call 2 are unchanged, at 1,550 and 1,900. Work out calls 3 and 4 and the total, then compare with 13,550.

Show a solution

Call 3 = 1,900 + 50 + 40,000 = 41,950. Call 4 = 41,950 + 50 + 150 = 42,150. Total = 1,550 + 1,900 + 41,950 + 42,150 = 87,550 input tokens, about 6.5 times the 13,550 of the careful design, for the same question. Retrieval that returns a few good chunks is what keeps your cost per request down. It may also give a better answer, because of context rot.

Summary 2 min

  • The context window is everything the model sees on a call: system prompt, tool definitions, history, tool results and its own reply. The model keeps nothing between calls; your program re-sends it.
  • Within a session the context grows, so late steps cost more and a bigger context can recall worse (context rot).
  • Between sessions, nothing survives unless it was saved to storage and loaded back. Save what stays true; fetch live facts live.
  • For long manuals, retrieve a few matching chunks instead of loading everything. Keyword search catches exact codes; embeddings catch meaning; use both when you can.

Say it in your own words: without looking, explain to a teammate why the assistant will not remember Monday's training on Wednesday unless you build something, and what you would build.
