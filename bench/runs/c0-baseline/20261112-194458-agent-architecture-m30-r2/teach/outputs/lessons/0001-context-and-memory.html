Context and memory in an agent

By the end of this lesson you can say exactly what the model sees at each step of the makerspace assistant, what it forgets between sessions, and how notes and retrieval fill the gap.

Objective O3: explain context and memory in an agent About 30 minutes Builds on the agent loop (your quiz 0001)
Why this matters for you

Your design review will ask three questions you can now answer: what does the assistant keep in context, what does it save between visits, and how does it find the right page in a long manual? The answers also decide your cost per request, which is the number your sponsor cares about.

Warm-up 2 min

Before new material, pull something from memory. Answer in your head or on paper first, then check.

Recall

In the agent loop, the model asks for a tool and the program runs it. What does the program do with the result, and how many separate model calls does a request with three tool calls need?

Check your answer

The program sends the result back to the model as part of its next input and calls the model again. Three tool calls plus the final answer make four model calls. Today's question is what is inside each of those calls, because that is where context and cost come from.

Here is the idea in one picture before the details. Suppose a student asks, “Is the laser cutter free Friday, and can I cut acrylic on it?” The assistant calls check_calendar, then search_manuals, then answers. The model does not hold a running thought across those steps. Each call starts from whatever text the program hands it, and nothing else.

The context window: everything the model sees 6 min

The context is the set of tokens the model is given when it generates a reply, and the context window is the limit on how many tokens that can be. A token is a chunk of text, roughly a short word or a piece of a long one. Anthropic describes the context window as the model's “working memory”, and says it holds all the text the model can reference when generating a response, including the response itself (Claude docs: context windows).

Start with a concrete case. The program builds this request for the laser cutter question:

system prompt   "You are the makerspace assistant. Be brief. Never book
                 without confirming the student's training."      ~300 tokens
tool list       check_calendar(...), search_manuals(...),
                 book_machine(...)  with their descriptions         ~1,700 tokens
user message    "Is the laser cutter free Friday...?"              ~50 tokens

That is about 2,050 tokens before the model has said a word. Notice something that surprises many people: the tool descriptions count. The docs say everything in the request counts toward the window: the system prompt, every message including tool results, and the tool definitions, plus the output the model generates (Claude docs). This is why your tool descriptions should be clear but not bloated: every word is paid for on every call.

Now the most important fact in this lesson. The model is stateless: it keeps nothing from one call to the next. Anthropic's docs describe each turn as an input phase containing all previous conversation history plus the current message, and an output that becomes part of the input for the next turn (Claude docs). So when the assistant seems to “remember” your question while it calls three tools, what is really happening is that the program re-sends the question every single time.

Think of a notepad passed to a new colleague at every step. The colleague has no memory of the previous step, but the notepad has everything written so far. The notepad is the context.
A common mix-up

“The model remembers the conversation.” It is tempting because chat apps feel continuous. But the continuity lives in the program, which stores the messages and sends them again. If the program sends only the newest message, the model has no idea what came before. You will see this misconception again below, at the level of whole sessions.

The third option. The model keeps nothing between calls, so the program re-sends everything: system prompt, tool list, question and every earlier tool request and result.

Between steps: the context grows 7 min

If every call re-sends everything, then each step makes the next call bigger. Let us put numbers on it. Say each tool request is 50 tokens and each result is 1,000 tokens (one manual page is about that). Starting from 2,050 tokens:

Model callWhat is sentInput tokens
1setup and question2,050
2+ request and result of tool 13,100
3+ request and result of tool 24,150
4+ request and result of tool 35,200

The total you send is 2,050 + 3,100 + 4,150 + 5,200 = 14,500 input tokens, even though the student only ever supplied about 50 tokens of their own. Input tokens are what you pay for, so cost per request grows faster than the number of steps: each extra step costs more than the one before it. (Prompt caching can make the repeated part cheaper to pay for, but the docs are clear that cached tokens still occupy the window: caching changes what you pay, not whether they count.)

There is a second cost besides money: quality. Anthropic's engineering team writes that as the number of tokens in the window increases, the model's ability to accurately recall information from that context decreases, an effect they call context rot. They describe context as a finite resource with diminishing returns, and the goal as finding the smallest set of high-signal tokens that gets the result you want (Effective context engineering for AI agents). The degradation is gradual, not a cliff.

A common mix-up

“A bigger window means I can just paste in all the manuals.” The docs list current models with windows up to 1M tokens, yet they also state that more context is not automatically better and that curating what is in context matters as much as the space available (Claude docs). Even if all your manuals fit, you would pay to re-send them on every call, and the model would have more noise to sift for the one relevant page.

Three ways to keep the growing context in check

When the steps-so-far part gets heavy, an agent program can trim it. The Anthropic post names several techniques:

  • Clearing old tool results: once the model has used a manual page, drop that page's text from later calls. The post calls this a lightweight form of compaction.
  • Compaction: when a conversation nears the limit, have the model summarize it, then start a fresh window from that summary, keeping what matters (decisions, open problems) and dropping redundant output.
  • Sub-agents: a helper explores in its own clean window and returns only a short summary, which the post says is often 1,000 to 2,000 tokens. You will meet this properly in the multi-agent lesson, so just note it for now.

All three are cited from Effective context engineering for AI agents. For a makerspace assistant most requests are short, so the first one, clearing old tool results, is likely the only one you need. Notice that this connects to your budget: trimming is how you stop the table above from growing.

Check yourself

Your assistant retrieves a 1,000-token manual page, uses it, then keeps working for ten more steps. What is the best way to limit its cost?

Show the answer

The middle option. Text you remove is not sent and not billed. Text you merely tell the model to ignore is still sent and still counts.

Between sessions: the model remembers nothing 7 min

A session here means one conversation: from when a student starts talking to the assistant until it ends. What happens on Monday when a student says, “I finished the laser cutter training,” and then comes back on Thursday?

The answer follows from the last section. The context lives in the program's variables, for as long as the program keeps them. When the session ends, the messages are gone, unless the program chose to save them. On Thursday the program builds a fresh context: system prompt, tool list, new question. The model has no way to know about Monday, because nothing from Monday is in the text it is given.

A common mix-up

“The assistant learns from each student and remembers them.” Training happened before you ever called the model, and your conversations do not change it. The Claude docs make the same distinction: the context window is a working memory, different from the large corpus the model was trained on (Claude docs). If a fact is not in the current context, the model does not have it. It may guess, and a confident wrong guess is the failure you already noticed in chatbots.

So memory in an agent means a store outside the context window, that the program writes to and reads from, plus a rule for what gets brought back into context. The Anthropic post calls the simplest version structured note-taking, or agentic memory: the agent regularly writes notes to storage outside the context window, and pulls them back in at later times. Their examples include a to-do list in Claude Code and a NOTES.md file, and they describe Claude playing Pokémon keeping track of progress over thousands of steps and, after a reset, reading its own notes to continue (Effective context engineering for AI agents). Anthropic also offers a file-based memory tool for this, which you can read about in the memory tool docs.

For the makerspace assistant the memory has two jobs, and they are different:

Kind of factExampleWhere it should live
Facts the program must get rightDana completed laser cutter training on 3 MarchA database the program owns; the model never writes this itself
Soft notes that help the conversationDana usually cuts 3 mm plywoodA short notes file the model can add to through a tool
Rules and tool listsNever book without trainingThe system prompt, the same for everyone

Separating these matters for defending your design. A training record decides whether someone may use a laser cutter, so a model's loose note is the wrong place for it. Whatever is stored must also be put back into the context to have any effect: a notes file nobody reads is just a file. At the start of a session the program looks up Dana, pulls her record, and adds a line such as “Dana: laser cutter training done” to the context. Keep these loaded notes short, since they are re-sent on every call like everything else.

The third option. Saved notes only matter once their text is in the context for a call. Reading them can be done by the program at session start, or by the model asking for them through a tool.

Retrieval: finding the right page 6 min

Notes are one kind of outside store. The other is the one you started with: the machine manuals. The laser cutter manual might be 120 pages, perhaps 60,000 tokens. Sending all of it on every call would be expensive and noisy, as section 2 showed. Retrieval means searching a large store and putting only the few most relevant pieces into the context.

Here is a worked case. A student asks, “How do I set the focus on the laser cutter?” A retrieval setup does this:

  1. Prepare once, ahead of time. Split each manual into small pieces, called chunks, such as a page or a section, and build a way to search them. One common way is embeddings, where text is turned into numbers so that pieces with similar meaning can be matched; plain keyword search also works for manuals full of model numbers and error codes.
  2. At question time, search for the chunks that best match the question.
  3. Put the top few chunks into the context, say three chunks of 500 tokens, so about 1,500 tokens instead of 60,000.
  4. The model answers from those chunks, and ideally says which page it used so the student can check.

Two ways to run the search

The Anthropic post separates two designs. In pre-inference retrieval (embedding-based), relevant context is surfaced before the model runs, and the program puts it in the request. In just-in-time retrieval, the agent keeps lightweight references such as file paths, stored queries or links, and loads data into context at run time by calling tools. The post says Claude Code does a hybrid: it loads some files up front, and uses search commands to explore as needed. The trade-off it names is that just-in-time is slower and needs good tool design, while pre-inference is faster (Effective context engineering for AI agents).

You have already built the second kind in your head: search_manuals(query) is a just-in-time retrieval tool. The model decides when to call it and with what query, and the result enters context as a tool result. The first kind would be the program searching on the student's question before the first model call. For a makerspace, where nearly every question is about a manual, either works. A small hybrid is plausible: load the machine's one-page safety rules up front, and let the model call the search tool for details.

A common mix-up

“Retrieval means the model looks the answer up.” The model never touches the manual. The search runs in your program, and the model only sees the text that comes back. So if the search returns the wrong chunk, the model answers from the wrong chunk, confidently. Most failures of a manual assistant are retrieval failures, not model failures, which is why you should test your search separately.

The first option. The model's whole view of the manual is the chunks retrieval gives it, so a bad retrieval produces a confident answer from the wrong text.

Worked example and practice 4 min

Worked example: price one request

A student asks for the CNC router's bit change steps. The setup (system prompt, tools, question) is 2,000 tokens. The assistant makes one search call: the request is 50 tokens and the result is 1,500 tokens. Then it writes the answer. How many input tokens did the two model calls use in total?

  1. Call 1 sends only the setup: 2,000 tokens.
  2. Call 2 sends the setup plus the tool request and result: 2,000 + 50 + 1,500 = 3,550 tokens.
  3. Total input: 2,000 + 3,550 = 5,550 tokens. The 1,500-token page was paid for once, in call 2. A third call would pay for it again.
Your turn

A request starts with a 3,000-token setup. Each of two tool calls adds 600 tokens (request plus result) to the context, and then the model writes the final answer. First step: list how many model calls there are. Then find the size of each call's input and the total.

Show a solution

Two tool calls plus the final answer make three model calls. Call 1 sends 3,000. Call 2 sends 3,000 + 600 = 3,600. Call 3 sends 3,600 + 600 = 4,200. Total: 3,000 + 3,600 + 4,200 = 10,800 input tokens. If the tool results had been cleared after use, calls 2 and 3 would be smaller.

Summary 2 min

  • The context window is everything the model sees in one call: system prompt, tool list, messages and tool results. The model keeps nothing between calls.
  • Between steps, the program re-sends everything, so the context and the input cost grow with each step, and long contexts can also hurt recall (context rot). Clear or summarize what is no longer needed.
  • Between sessions, the model remembers nothing. Memory is a store outside the context, written and read by the program, whose contents only matter once placed in the context.
  • Retrieval searches a large store, such as manuals, and puts only the best few chunks into the context. The model never sees what the search did not return.
