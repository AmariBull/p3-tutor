Context and memory: what the assistant sees, keeps and looks up

By the end of this lesson you can say, for the makerspace assistant, what sits in its context at each step, what is lost when a session ends, and which job belongs to notes and which to retrieval.

Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three are context and memory decisions, and you will have to defend them at your design review.

Warm-up 2 min

Before new material, pull something from memory. You already know the agent loop, so use it.

Recall

The assistant gets the question "Is the laser cutter free on Friday?" and calls a calendar tool. In your own words: what does the program do with the tool's result, and what happens next? Answer before you open the box.

Check your answer

The program takes the result and sends it back to the model as part of its next input, then calls the model again. The model uses the result to pick its next action or to write the final answer. Today's lesson is about that "next input": what exactly is in it, how big it gets, and what happens to it when the conversation ends.

The context window 5 min

Start with a concrete case. A student types: "Can I use the laser cutter, and how thick can the plywood be?" The model does not see the student, the makerspace or the manual. It sees only text that your program puts in front of it on that call. That text is its context.

The context is the set of tokens included when the model generates a reply (Anthropic, Effective context engineering for AI agents). A token is a small piece of text, often a short word or part of a word; you met tokens in the first session, since the model writes one at a time. The context window is the maximum number of tokens the model can take in on one call. Anything outside the window, or simply not included on this call, does not exist for the model.

For the makerspace assistant, the context on a typical call holds:

  • the system prompt: your standing instructions ("You answer questions about makerspace machines; never book without confirming the time");
  • the tool descriptions: the name, purpose and parameters of each tool, which is how the model knows what it can call;
  • the conversation so far: the student's messages, the model's earlier replies and tool requests;
  • the tool results: calendar entries, manual passages, the training record.

Bigger is not free, and it is not always better

Two facts matter for your design. First, you pay by the token, for what goes in and for what comes out, so a bigger context is a bigger bill. Second, a full window is not a better-informed model. Anthropic's engineers describe context rot: as the number of tokens in the context grows, the model's ability to recall information from it decreases (same article). They suggest treating context as a limited resource with an "attention budget" and aiming for the smallest set of high-signal tokens that gets the job done.

For you this is a design rule: do not ask "how much can I fit?" Ask "what does the model need to see to do this step?"

A common mix-up

"A bigger context window means the assistant can just read everything, so I need no other design." It is tempting because the window numbers keep growing. But everything in the window is paid for on every call, and recall gets worse as it fills. Pasting a whole manual into every request is both expensive and less accurate than giving the model the two right pages.

What is kept between steps 6 min

Now connect this to the loop you already know. Here is the surprising part: the model keeps nothing between calls. Each step of the loop is a separate call, and the model starts every call blank. The only reason it appears to remember the last step is that the program sends the earlier steps again, as part of the new context.

Think of a clerk with no short-term memory who reads a notebook from page one every time you speak to them. The notebook is the context. The program owns the notebook and adds a line after every step; the model only reads it. The Claude memory tool docs say the same about the other direction: memory lives in your application, not in the model (Claude docs, Memory tool).

Why this drives your budget

If every call re-sends the whole notebook, then the cost of a request is not the size of the final context. It is the sum of the input of every call. Long tool results hurt most, because once a result is in the notebook it is re-sent on every later call. (Tricks such as caching repeated text can make re-sent text cheaper; the contextual-retrieval article mentions prompt caching for exactly this reason. The principle stays: re-sent text is text you pay for.)

Worked example: counting input tokens

A student asks, "Is the laser cutter free tomorrow at 3 pm, and do I need training?" Numbers are made up to show the pattern. The setup (system prompt, tool descriptions, question) is 2,000 tokens. Each tool request the model writes is 50 tokens. The calendar result is 400 tokens, the manual passages 3,000, and the training record 200. The model is called four times: three tool requests, then the answer.

  1. Call 1 input: the setup, 2,000 tokens.
  2. Call 2 input: setup + the model's request (50) + calendar result (400) = 2,450.
  3. Call 3 input: 2,450 + request (50) + manual passages (3,000) = 5,500.
  4. Call 4 input: 5,500 + request (50) + training record (200) = 5,750.
  5. Total input across the request: 2,000 + 2,450 + 5,500 + 5,750 = 15,700 tokens, although the final context is only 5,750.

Notice that the 3,000-token manual passage is paid for twice, in calls 3 and 4. A smaller passage, or dropping it once the model has used it, would save more than anything else here.

When the context grows too big 4 min

A long chat, or an agent that makes many tool calls, will push toward the window limit and the budget long before it finishes. Your program, not the model, decides what to drop. Anthropic describes three main techniques (Effective context engineering):

TechniqueWhat it doesMakerspace example
Clearing tool resultsRemoves raw tool output from earlier steps that is no longer needed.Once the assistant has picked a free slot, the full week of calendar entries can go.
CompactionSummarizes the conversation and starts a new context window with the summary.After 40 messages about a project, keep "student wants 3 hours on the CNC, prefers Tuesday, needs training".
Sub-agentsA separate agent works in its own clean context and returns only a short summary.Not needed for your first design; you meet it in a later lesson.

Compaction is a trade: you gain room and lose detail. The article advises tuning it to keep everything important first, then trimming. What is important is a design decision: for you, the student's goal, decisions already made and open questions, not the raw page text.

What is kept between sessions: notes 6 min

A session is one conversation: from the student opening the chat until it ends. When it ends, its context is gone. Tomorrow's session starts with the setup and nothing else. If Sam passed the laser cutter training on Monday and comes back on Thursday, the assistant has no idea, unless something outside the context recorded it.

A common mix-up

"The assistant is an AI, so it remembers earlier conversations by itself." It is tempting because a chatbot you use daily seems to know you. That apparent memory is something its builders added: stored notes that get loaded back in. A bare model call, and an agent you build without a memory design, remembers nothing. This is the reason the makerspace assistant needs one.

The fix is memory in the agent sense: information saved outside the context window, which the agent can load into a later context. Anthropic calls one pattern structured note-taking: the agent regularly writes notes to storage outside the context window and reads them back when needed. Their example is an agent playing a game that kept tallies across thousands of steps and rebuilt its state from its notes after its context was reset (Effective context engineering).

The Claude memory tool turns this into a tool the model calls, so it fits the loop you already know. The model requests file operations on a /memories directory (view, create, edit, rename, delete), and your application runs them against storage you control, such as a per-user folder or a database (Memory tool docs). When enabled, Claude checks its memory directory before starting a task, records progress as it goes, and reads memory back in later conversations.

What belongs in the notes

Notes cost tokens when they are loaded, so the same rule applies: save facts that will matter later, and keep them short. For the assistant, a good record per student is small and checkable.

/memories/students/sam.md
- Trained: laser cutter (Mon 3 Nov), 3D printer (not yet)
- Usually books Tuesday afternoons
- Open request: wants CNC time, needs training first

Two cautions from the docs. Memory can hold sensitive information, so cap file sizes, delete stale files and validate every path your handler accepts, since a path such as /memories/../../secrets.env could reach files outside the memory directory (Memory tool docs). And notes can be wrong or out of date: a training status that was true in November may be wrong now, so decide which facts the assistant should trust from notes and which it should re-check with a tool, such as the booking calendar.

Finding the right page: retrieval 5 min

Notes hold what the assistant learned. The manuals hold what the makerspace already knows, and they are long. You have two ways to give the model a manual's contents. Anthropic's guidance on this: if a knowledge base is smaller than about 200,000 tokens (roughly 500 pages), you can include all of it in the prompt, and prompt caching makes that cheaper and faster; for larger knowledge bases you need retrieval (Anthropic, Contextual Retrieval). Check your own manuals' total length first: if they are small, the simplest design may be the best one.

Retrieval means searching a collection and putting only the best matches into the context. In the common pipeline, the manuals are split into chunks of a few hundred tokens each. Each chunk is turned into an embedding, a list of numbers that captures its meaning, and stored. When a question arrives, the system embeds the question, finds the chunks whose meaning is closest, and adds those chunks to the context (Contextual Retrieval).

Meaning-based search has a weak spot: exact strings. A student who asks about "error E-47" needs the chunk containing that exact code, and an embedding may return chunks that are about errors in general. A keyword method called BM25 matches exact terms, so the article recommends combining both (Contextual Retrieval).

Retrieval has a second way to work, which fits an agent well: just-in-time retrieval. Instead of searching once at the start, the agent keeps lightweight references, like the names of manual sections, and loads the one it needs through a tool call when it needs it. Anthropic notes it is slower than loading everything up front and that a hybrid is common: some key text up front, the rest on demand (Effective context engineering). You already have such a tool in your plan: search_manuals.

A common mix-up

"Retrieval and memory are the same thing." Both bring text into the context, which is why they blur. But memory is what the agent saved about this student or task; retrieval is searching material that already exists, such as manuals. They are often built differently and fail differently: stale notes versus a missed page.

Check yourself

Worked example and practice 3 min

Worked example: where does each piece live?

Student Sam writes: "I want to cut 6 mm acrylic on the laser cutter on Friday afternoon." Place each piece of information.

  1. Sam's training status. Specific to Sam, needed across visits, learned earlier. It lives in notes, loaded at session start (and, if the record is critical, confirmed with a tool).
  2. Whether the laser cutter is free Friday. Changes constantly. It is not saved; the assistant calls the calendar tool and the result sits in context for this task only.
  3. Acrylic settings for 6 mm. Lives in the manual. It is retrieved: search, bring in only the matching chunk, then clear it once the answer is given.
  4. Sam's chosen Friday slot. Needed again at the end of this chat, so it stays in context; after booking, a short line goes into notes ("booked laser Fri 2 pm").
Your turn

A different student, Priya, asks: "Can I use the vinyl cutter? Last time you said I needed a safety check, and I'd like Wednesday at 4." Decide for each of these whether it belongs in notes, in a tool call, in retrieval from the manual, or in the live context. First one done: "Priya completed the safety check last week" goes in notes. Place the other three: (a) the vinyl cutter's blade depth setting, (b) whether Wednesday at 4 is free, (c) Priya's request for Wednesday at 4 during this chat.

Show a solution

(a) Retrieval from the manual: it is in the manuals and the same for everyone. (b) A tool call to the calendar: it changes, so never trust a saved copy. (c) Live context: it is needed for the next few steps of this chat; only after booking would a short summary go into notes.

Summary 2 min

  • The context is everything the model sees on one call: system prompt, tool descriptions, conversation and tool results. The window limits it, and a fuller window recalls worse and costs more.
  • The model keeps nothing between calls. Your program re-sends earlier steps each time, so cost is the sum of every call's input.
  • Trim by clearing old tool results or compacting into a summary.
  • Nothing survives a session unless saved: notes in storage outside the context hold what was learned about a student or a task.
  • Retrieval searches existing material, like the manuals, and brings in only the best chunks.
